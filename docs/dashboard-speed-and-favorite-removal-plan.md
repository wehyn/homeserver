# Dashboard Performance and Favorite Removal Implementation Plan

> **For Hermes:** Use the `test-driven-development` skill for code-producing tasks. Implement in small, independently verifiable commits; preserve Nimbus's local-first, server-only SQLite, accessibility, and security boundaries.

**Goal:** Remove the unused Favorites concept from the application contract and user experience while improving Nimbus's first usable render, recurring telemetry/health efficiency, process-detail responsiveness, and repeat navigation behavior without changing visual language, operational status semantics, or user data.

**Architecture:** Keep the Next.js App Router and server-only `lib/db.ts` boundary. First repair and instrument the browser-validation path, then remove Favorites with inert legacy-column compatibility, then make only measurement-backed performance changes. Keep health checks, operational API responses, and mutable SQLite data out of the service-worker cache. Prefer request coalescing, bounded work, and deferred secondary UI over broad rewrites.

**Tech Stack:** Next.js 15 App Router, React 19, TypeScript strict mode, Framer Motion, Lucide React, Node `node:sqlite`, SQLite/WAL, Playwright, npm, Docker/Compose, optional local metrics agent.

## 1. Project-manager review: scope and decisions

This is a cross-cutting change, not a single UI cleanup. The implementation must cover five linked surfaces:

1. **Product contract:** `ManagedApp`, mutation payload validation, database row mapping, seed/default records, API responses, and all fixtures/tests.
2. **User experience:** settings form, copy, launcher rendering, mutation behavior, focus/Escape/inert behavior, responsive layout, and accessible state announcements.
3. **Performance:** first-screen JavaScript/hydration, app/activity/overview/health request waterfall, icon fallback requests, recurring host sampling, health fan-out, Docker reconciliation, process collection/table rendering, activity growth, and PWA asset behavior.
4. **Operational/security boundaries:** server-only SQLite, local/read-only Docker discovery, bounded external health/icon requests, SSRF protections, insecure-TLS opt-in, no API caching, no SVG execution, and stale-status/error semantics.
5. **Release validation:** unit/type/build/browser/CI gates, clean test data, desktop/mobile geometry, accessibility interactions, production bundle/request evidence, deployment behavior, and documentation/release notes.

### Decisions to make before coding

- **Legacy SQLite column — recommended:** leave `apps.is_favorite` physically present and inert for the first release. Remove it from the TypeScript/API/write contract, ignore it when reading rows, and do not run a destructive table recreation. A physical drop is a separate versioned migration only after deployment policy, backup, rollback, and multi-version compatibility are approved.
- **Initial-data strategy:** compare server-rendered initial app/overview data with a narrowly scoped bootstrap response. Do not make `/api/apps` perform overview, health, or optional discovery side effects. Keep health asynchronous so a broken service cannot block first paint. Choose the smallest option that materially reduces the measured waterfall.
- **Priority target — recommended ordering:** (a) first usable launcher on mobile and desktop, (b) repeat navigation/static-cache behavior, (c) steady-state polling and server resource use, then (d) modal/process-detail cost. Set numeric budgets only after measuring the existing app on the target machine; do not invent machine-specific values.
- **Icon expectation:** confirm whether every above-the-fold tile must show its remote icon immediately. Safe default: keep fallback glyphs and do not delay launcher usability; defer lower/overflow icons only if the product accepts that behavior.
- **Health semantics:** retain the existing 5-second overview refresh, 30-second health refresh, stale-last-known status behavior, race-safe persistence, and visible failure messaging unless a product decision explicitly changes freshness.
- **Retention policy:** define activity age and row-count bounds before implementing cleanup. Keep metric-history retention and chart ranges unchanged unless separately approved.

### Measured source/runtime map

#### Initial page and request waterfall

`app/page.tsx` is a large `"use client"` island. It owns app loading, activity, overview and health polling, mutation state, settings/system-detail modal orchestration, reduced-motion preference, clock updates, online/offline handlers, and `inert` management. The initial client dependency graph includes Framer Motion, launcher components, settings, the system detail modal, and the chart import.

On mount, the current client requests are independent for:

- `/api/apps` in `loadApps` (`app/page.tsx:109-123`, invoked at `129-131`).
- `/api/activity` (`app/page.tsx:133-142`, invoked at `144-146`).
- `/api/overview` (`app/page.tsx:148-167`, invoked at `173-177`), including a 5-second interval.
- Health requests begin only after app loading completes (`app/page.tsx:179-213`, effect `244-249`), one `/api/health?id=...` request per app with `healthUrl || url`, all launched with `Promise.allSettled`.

Health has a deliberate dependency waterfall, but the initial shell itself does not wait for all client requests: `app/page.tsx` renders `main.launcher` immediately with empty/loading state, and only the application grid is gated by `appsLoading`. `/api/activity`, `/api/overview`, health, and icon responses do not block the first shell paint; they do compete for network/server resources. The first usable app grid is still vulnerable to `/api/apps`, because `app/api/apps/route.ts:11-28` waits for optional Docker discovery before returning records. `lib/docker-discovery.ts:19-38` allows an agent request of up to about three seconds, while `agent/docker-discovery.ts:30-43,181-203,617-632` recursively scans Compose files and `:45-95` inspects containers serially. Measure the shell, loading state, app grid, first icon, overview, and first health result as separate milestones rather than describing all of them as one first paint. `loadApps` uses `cache: "no-store"` and on save the page updates local state, refreshes activity, then reloads `/api/apps` (`app/page.tsx:262-284` and especially `278`). That reload is not automatically redundant: the POST response lacks live `dockerDetails`, while the subsequent GET reconstructs them through `lib/docker-details.ts:4-21`. Remove it only after equivalent Docker metadata and URL behavior are proven. Delete waits 180 ms before its mutation (`286-302`). Online recovery launches app, overview, and health refresh together (`219-234`). The app health effect dependency string includes app identity/target/TLS settings, which restarts the interval when those values change.

First-screen UI is `visibleApps = apps.filter(app => app.isVisible)` (`app/page.tsx:260`); there is no Favorites view/filter. The launcher renders every visible tile plus the add tile. `app/launcher/launcher-components.tsx` owns tile/UI status; `app/launcher/icons.tsx:25-33` computes remote icon sources during render and uses a fallback after image errors.

#### Server and persistence

`app/api/apps/route.ts` exposes `GET`, `POST`, and `DELETE`. `GET` calls `listApps()` and optional Docker discovery/reconciliation; `POST` validates JSON with `parseManagedAppPayload`, calls `saveApp`, and returns the saved app; `DELETE` validates an ID and calls `removeApp`. Keep route responsibilities narrow and JSON-shaped.

`lib/db.ts` is server-only, opens `DATABASE_PATH` or `data/nimbus.db`, enables WAL, creates/patches the `apps`, `activities`, and `metric_snapshots` tables, seeds when empty, and adds columns for the evolving Docker/CasaOS/health contract. The current `apps` table declares `is_favorite INTEGER NOT NULL DEFAULT 0`; current seed insert and `saveApp` SQL include it; `fromRow` reads it. The current `listApps` uses `SELECT *`, which is helpful for legacy compatibility but makes explicit read/write projection worth considering after the contract change. `saveApp` preserves an existing status and health-generation, clears stale Docker metadata when explicit project/service linkage changes, and records an activity on create/update. `reconcileDockerApps` loops apps, repeatedly searches containers, and writes observed metadata on every matched reconciliation, including a changing `container_observed_at`.

`recordMetricSnapshot` inserts a sample and prunes by age; `listMetricSnapshots` orders chronologically. Activities have an index on `created_at DESC` but no age/count pruning; status changes and app mutations write activities. Any activity policy must be bounded and keep the five-event API/read behavior.

`lib/db-row.ts` converts a `ManagedApp` to SQLite named parameters; after removal it must not require a field that no longer exists in the in-memory contract. `lib/app-validation.ts` currently requires `id`, `name`, `description`, `category`, valid `url`, `color`, optional `healthUrl`, `allowInsecureTls`, valid `status`, valid `source`, boolean `isFavorite`, boolean `isVisible`, and integer `sortOrder`; preserve all non-Favorites validation and reject unknown/unsafe malformed values according to the current behavior. Its successful result currently spreads the input object, and `app/api/apps/route.ts` strips only `dockerDetails`, so removing the type check alone could let legacy `isFavorite` input survive into the returned object or SQLite named parameters. The implementation must explicitly allow-and-strip or deliberately reject that stale field. `lib/seed.ts` currently provides eight records and sets `isFavorite`; remove only the obsolete field, not the records or visibility/order.

#### Health, metrics, and external calls

`app/api/health/route.ts` resolves the target with `lib/health-target.ts`, permits only `http:`/`https:` URLs without credentials, uses `redirect: "manual"`, a 4.5-second timeout, and opt-in insecure HTTPS through `https.request`. It persists a result only when the generation/target snapshot still matches, preserving race safety. The normal `fetch` path returns after reading the status without consuming the response body; the insecure path resumes/drains it. Verify the actual Node fetch behavior and drain/cancel without weakening timeout, redirect, TLS, or SSRF safeguards.

`lib/health-client.ts` parses the JSON response and distinguishes valid, API-error, malformed, and transport-error results. Browser health fetches do not currently set `cache: "no-store"`; make HTTP caching behavior explicit even though the service worker bypasses `/api/*`. `lib/health-results.ts` applies only valid results whose app/target still match; no-op results preserve array/object identity. The server resolves a complete CasaOS target before `healthUrl`/`url` (`lib/health-target.ts:3-22`), while the page records `healthUrl || url` as the result target (`app/page.tsx:193-203`), so plan a shared actual-target contract or test/fix this parity before changing race guards. `lib/health-persistence.ts` tests generation/target-safe persistence. Preserve stale status on failed checks and activity refresh semantics; do not overwrite a newer status with an older request.

`app/api/overview/route.ts` gathers CPU, memory, storage, hardware-agent data, and history. CPU sampling intentionally waits about 100 ms on the first request to establish a baseline; hardware uses agent timeout plus local sysfs fallback (`agent/hardware.ts`), and metric history is sampled at one-minute intervals with 30-day retention. A 5-second UI interval can therefore repeatedly invoke host probing even though history writes are already throttled. Coalescing must not make `updatedAt` or the user-visible freshness claim misleading.

`app/api/activity/route.ts` returns the latest five activities. `app/api/metrics/history/route.ts` normalizes the range and returns chart points; `app/metrics-history-chart.tsx` is loaded by the system details modal and should not be in first-screen code if a measured dynamic boundary is safe.

#### Docker and agent work

`lib/docker-discovery.ts` bridges optional local Docker/Compose discovery. `agent/docker-discovery.ts` performs read-only Docker socket/Compose work, recursively scans Compose files, inspects containers sequentially, parses CasaOS metadata and Compose details, and reports unavailable/partial states. A client abort does not prove this server/agent work stops. Any optional-discovery deadline must cover the full route budget, traversal, and inspection, not only the individual request timeout. Preserve read-only GET-shaped Docker access and the no-broad-network/security policy. Compose environment parsing must also be checked for secret redaction before values reach `/api/apps` or the settings UI.

`lib/docker-details.ts` resolves detail data with repeated array `find`/`filter` matching by IDs, project/service, names, labels, or URL port. Preserve matching precedence and ambiguity safeguards if lookup maps are introduced.

`agent/process-agent.ts` reads `/proc` memory and process metadata, sanitizes commands, calculates CPU percentages, reports partial/warnings/`omittedCount` for unreadable processes, and currently returns every readable process. Memory collection reads every PID with unbounded `Promise.all`; CPU sampling reads candidates and metadata concurrently, so a response cap alone will not bound filesystem work if ranking still requires all candidates. `collectProcessorSnapshot` uses process reads needed for CPU/load. `app/api/processor/processes/route.ts` and `app/api/memory/processes/route.ts` expose snapshots but validate unlimited arrays and do not propagate request cancellation into the agent. `app/system-details-modal.tsx:48-82` fetches one endpoint immediately and every five seconds, sorts the entire process array on every snapshot/sort change, and renders one `<tr>` per returned process; its request path lacks the history chart's explicit request-identity guard. Existing tests already assert partial/omitted behavior for unreadable processes, so any top-N/cap contract must distinguish unreadable from intentionally omitted processes and preserve captions, warnings, totals, sort behavior, and accessible table semantics. The browser fixtures currently omit `omittedCount`, so they do not fully exercise the real contract.

#### Assets and PWA

`app/layout.tsx` globally loads Manrope and DM Mono through `next/font/google`; this is part of the visual language. `app/globals.css` is large and contains responsive/accessibility/layout rules; do not broad-rewrite it during a speed task. `public/sw.template.js` is source; `scripts/generate-sw.mjs` generates tracked `public/sw.js` from a hash/revision. The service worker does not intercept API requests and uses network-first navigation with an offline shell. It precaches offline/identity assets and handles selected same-origin static assets with a network-first-like fetch followed by cache fallback, currently awaiting `cache.put()` before returning a successful network response. Do not manually edit generated `public/sw.js`; if changing policy, update template/generator and run the build/prebuild.

The service worker's current navigation path correctly prefers fresh operational HTML online, while its static path may delay a response on cache-write work and can fall back to an older cached response if a post-fetch cache write fails. The initial application shell and hashed Next chunks are not explicitly precached (normal navigation will discover them); registration occurs only after production hydration (`app/pwa-register.tsx:5-14`). `scripts/generate-sw.mjs` hashes the service-worker template, manifest, layout, offline page, and identity icons, but not page code, global CSS, or generated chunk contents; hashed chunk URLs limit collisions, but update behavior still needs explicit testing. Measure repeat navigation and update/activation behavior before changing cache-first policy. Never cache `/api/*` or private operational responses.

The Docker build context also deserves a security check: `.dockerignore` excludes `data` and databases but not `.env*`, while `Dockerfile` copies the repository into the builder. Exclude local environment files from the build context without excluding `.env.example`, or use an explicit build-secret mechanism; do not inspect or copy secret values into tracked files.

### Phase 1 — Remove Favorites without breaking old databases

#### Task 1.1: Write contract regression tests first

**Objective:** Define the reduced app payload and legacy-row behavior before changing implementation.

**Test:** `lib/app-validation.test.ts`, `lib/db-row.test.ts`, plus a new focused database compatibility test if no existing database fixture can cover it.

**Steps:**

1. Update the validation fixture to omit `isFavorite` and assert a valid payload is accepted and the returned object has no own `isFavorite` property.
2. Assert malformed required fields still fail: missing/invalid ID, name, description/category/color, URL, health URL, TLS boolean, status/source, visibility boolean, and integer sort order.
3. Assert `toDatabaseRow` has no `isFavorite` key or obsolete SQLite named parameter.
4. Add a temporary SQLite database test using `DATABASE_PATH` only if the module's singleton lifecycle can be isolated safely; create an old-style `apps` table containing `is_favorite`, read it, save an app, and verify the column/value is not required for application output and is not destructively dropped. If singleton state prevents safe in-process isolation, test the SQL/schema policy through a subprocess or a dedicated test seam rather than altering production initialization for tests.
5. Add explicit tests for the chosen fresh-schema policy: either a new database retains the inert column or a new database omits it while old databases retain it. Do not leave that matrix implicit.
6. Test a legacy payload containing `isFavorite: true`, `false`, and an invalid value. Prefer accepting and stripping it for rolling-client compatibility; alternatively assert a deliberate 400 response. In either case, verify it never reaches SQLite or API output.

**Acceptance:** Tests express the new contract, legacy-input policy, fresh-schema policy, and old-schema readability before implementation changes.

#### Task 1.2: Remove Favorites from shared types and row/payload mapping

**Objective:** Make `ManagedApp` and API mutations stop carrying the obsolete property while preserving old SQLite files.

**Modify:** `lib/types.ts:19-49`, `lib/app-validation.ts:12-42`, `lib/db-row.ts`, `lib/db.ts:22-71,97-131,247-268`, `lib/seed.ts`.

**Steps:**

1. Remove `isFavorite` from `ManagedApp`, seed records, blank/default app objects, and all new-record constructors.
2. Remove it from validation and `toDatabaseRow`.
3. Keep `is_favorite` in `CREATE TABLE IF NOT EXISTS` for compatibility with newly initialized databases that must remain schema-compatible, unless a migration policy explicitly changes this; do not assume removing it from the CREATE statement alters existing tables.
4. Stop selecting it into `ManagedApp` output by using an explicit application column projection or simply ignore the legacy property in `fromRow`. Ensure `saveApp` bootstrap INSERT and upsert remove `is_favorite`, `@isFavorite`, and the `ON CONFLICT` assignment. If new databases omit the column while old databases retain it, use a compatibility-aware write path or explicitly support only the documented schema matrix; test both expectations rather than relying on SQLite defaults.
5. Do not silently `ALTER TABLE DROP COLUMN`, rebuild, delete, or reseed a user's database.
6. Preserve app status/health generation and Docker metadata behavior.

**Acceptance:** Valid reduced payloads reach `saveApp`; output never exposes Favorites; old databases with `is_favorite` remain readable and preserve its value; new-row writes succeed; no destructive migration occurs.

> **Important schema nuance:** If the write SQL removes `is_favorite` from the INSERT but keeps a legacy column with a default, existing/new schemas work. If the application must support databases created without the column, avoid a fixed SQL path that assumes it exists. Decide whether the first release's schema always includes the inert column; document that exact compatibility matrix rather than leaving it implicit.

### Phase 2 — Repair validation and establish a trustworthy browser path

**Objective:** Prevent inherited environment and stale build output from masking browser regressions.

## 4. Risks, tradeoffs, and rollback

- **Bootstrap/server rendering:** fewer client waterfalls can increase server TTFB or couple the route to host sampling. Keep health and optional discovery out of the critical path; roll back if first usable render or TTFB worsens.
- **Overview TTL/coalescing:** reduces work but can make telemetry stale. Use a short documented TTL, preserve `updatedAt`, and roll back if freshness becomes misleading.
- **Health concurrency/pause:** reduces bursts but can delay status updates. Prefer in-flight coalescing/bounded concurrency before lowering visible frequency; preserve last-known statuses and errors.
- **Docker discovery:** a deadline can omit optional metadata. Return local records promptly and expose partial/unavailable state rather than failing the registry or silently replacing metadata.
- **Icon fallback/cache:** caching private or unvalidated content risks data leakage/security issues. Validate first, keep scope private/bounded, and retain safe fallback glyphs.
- **Dynamic modal imports:** reduce initial JS but add open-time delay. Use an accessible loading state and skip if the measured gain is trivial.
- **Process cap/virtualization:** caps improve safety but can hide rows. Prefer explicit totals/omitted reasons; never label a capped list “all readable processes.”
- **Activity pruning:** deletes old operational history. Define retention before coding and retain recent rows; do not conflate it with metric retention.
- **Service-worker policy:** caching mutable data can show stale operational truth. Keep API bypass and validate revision/update/offline behavior.
- **Legacy schema:** dropping a column can destroy compatibility. Recommended rollback is no physical schema change; any future drop must be a versioned, backed-up, tested migration.
- **Browser setup:** a passing build is not browser evidence. Keep startup/environment errors separate from product failures and test with a clean dev/production lifecycle.
- **Generated artifacts:** prebuild changes `public/sw.js`; `.next`, databases, agent output, Playwright output, and test results are runtime artifacts, not implementation files.

Before implementation, obtain explicit answers for:

1. Retain the legacy `is_favorite` column inert for the first release? **Recommended: yes.**
2. Choose server-rendered initial data, a bootstrap response, or no architecture change after baseline measurement.
3. Set the primary performance target and measurement device/network; establish budgets from baseline rather than guessing.
4. Are all launcher icons required immediately, or may below-fold icons be deferred?
5. May process detail responses cap rows/top-N, or must every readable row remain available via accessible virtualization?
6. What activity age/max-row retention policy is acceptable?
7. Should CI add `npm test` and `npm run build:agent` gates and a structural performance smoke test?
8. Does the supported deployment run one Next process/SQLite writer, and may in-process caches be used? If multiple replicas are possible, in-process TTLs/coalescing are only local optimizations and need a different shared-cache policy.
9. Is there a release-note/changelog convention to update?
